# 动态模板配置项目全量交付审计与迁移蓝图设计

> 适用范围：围绕 `req/req.md` 与 `req/supplement.md` 定义的“动态模板配置 + 基于配置生成业务模板”项目，形成一份可交付的全量审计、迁移蓝图、验收矩阵与证据包设计。

---

## 1. 设计目标

本设计不是直接实现方案，而是为了产出一套**完整项目交付审计 + 公司内迁移蓝图**的总交付结构，用来回答以下问题：

1. 当前项目是否已经达到“完整项目交付”标准。
2. 当前项目是否满足后续迁移到公司内环境的前置条件。
3. 当前代码、现有 spec/plan、以及需求文档之间有哪些偏差。
4. 如果不满足目标，缺口在哪里、风险级别是什么、应该如何整改。

---

## 2. 范围与基准

### 2.1 业务范围基准

业务范围与功能边界以 `req/req.md` 与 `req/supplement.md` 为准，聚焦于：

- 动态模板配置
- 基于配置生成业务模板
- 模板/版本/布局/字段/组件/查询/数据源/合同录入的核心闭环
- 嵌套组件、弹窗草稿、查询回填、外部数据映射/对比等关键流程

不主动扩展到与当前需求文档无关的额外平台能力。

### 2.2 架构与交付基准

架构、E2E、交付标准以用户口述要求为严格基准：

- Controller 使用 CXF 风格
- Controller 仅持有 `XxxReq` / `XxxRsp`
- `XxxReq` / `XxxRsp` 放在 adapter/controller 层自己的包中
- Application 层只持有 DTO，并保持薄层编排
- Domain 层承载充血模型、聚合根、聚合、值对象、仓储接口、领域流转语义
- Infrastructure 层持有数据实体、仓储实现、外部系统实现
- 持久化层禁止使用 MyBatis-Plus
- 只能使用原生 MyBatis
- 必须使用真实 XML，命名为 `xxx.opengauss.xml`
- XML 文件名禁止带 `Entity`，例如 `User.opengauss.xml`，不使用 `UserEntity.opengauss.xml`
- 基础设施层数据实体类保留 `Entity` 后缀，例如 `UserEntity`
- 领域对象不带 `Entity` 后缀，例如 `User`
- 转换统一使用 MapStruct
- 垂直调用必须成立：Controller → Application → Domain → Infrastructure
- E2E 必须是浏览器真实操作证据，不接受仅接口或单测替代
- JSONB 链路、几千量级数据量下的查询路径与优化证据必须成立

### 2.3 外部权威基准

审计将同时对照以下外部基准：

- DDD 权威定义（包括 Thoughtworks 常见实践语义）：聚合根、聚合、值对象、界限上下文、领域流转
- CXF 官方技术文档与约定
- 原生 MyBatis 与 XML 映射最佳实践
- MapStruct 官方转换约定
- openGauss / PostgreSQL JSONB 能力与查询/索引最佳实践
- 浏览器 E2E 与交付级验证最佳实践

### 2.4 代码审计基线

审计同时输出两套现状：

1. **已提交代码基线**：当前仓库已提交状态
2. **当前工作区基线**：加上未提交改动后的状态

### 2.5 判定口径

本次交付采用双结论制：

1. **整体是否可交付** 的硬结论
2. **功能 / 架构 / 性能** 三个维度的分项结论

同时存在一票否决项，只要触发，必须明确标记在整体结论和分项结论中。

### 2.6 一票否决项

以下事项视为一票否决：

- 持久化仍依赖 MyBatis-Plus，而非原生 MyBatis + XML
- 未形成严格的 DDD 分层与对象边界
- 浏览器 E2E 未覆盖核心闭环
- JSONB 链路与几千量级查询优化无有效证据

### 2.7 MVP 口径

功能完成度按 **MVP 草稿态** 理解，但架构口径不放松：

- 功能结论：允许按 MVP 阶段评估完成度
- 架构结论：必须按最终迁移目标严格审计
- 任何“先跑通再说”的过渡实现，都记录为架构缺口

## 3. 交付物结构

### 3.1 主报告

主报告面向三类读者：

- 用户本人：判断是否值得继续、哪里必须返工
- 研发团队：了解缺口、目标蓝图与整改顺序
- 汇报/验收方：快速看到结论、风险、证据入口

主报告包含：

1. 执行摘要
2. 范围、基准与判定规则
3. 现状功能闭环审计
4. 浏览器 E2E 审计
5. 架构与 DDD 审计
6. 持久化与 MyBatis XML 审计
7. JSONB 与性能审计
8. 目标蓝图与迁移路线
9. 验收矩阵
10. 结论与整改建议

### 3.2 证据包

证据包与主报告分离，保证每个结论可追溯。建议结构：

- `screenshots/`：浏览器关键步骤截图
- `browser-flows/`：E2E 场景步骤记录
- `api-evidence/`：关键接口请求/响应样例
- `sql-and-xml/`：关键 XML、SQL、JSONB 查询路径说明
- `performance/`：EXPLAIN、索引说明、查询路径分析、量级判断
- `file-notes/`：关键文件说明与垂直调用链角色说明

### 3.3 迁移检查表

独立输出一份可执行检查表，用于后续迁移到公司内环境时直接核对。

---

## 4. 报告章节设计

### 第 1 章：执行摘要

只回答管理层最关心的内容：

- 当前能否作为完整项目交付
- 当前能否作为公司内迁移候选基础
- 一票否决项有哪些
- 若整改，主要成本落在哪几块

### 第 2 章：范围、基准与判定规则

明确：

- `req/` 两个需求文档是业务范围基准
- 架构 / E2E / 交付标准按用户口述严格要求
- 外部基准来源
- 代码基线（已提交 / 工作区）
- 双结论制与一票否决项口径

### 第 3 章：现状功能闭环审计

围绕完整项目交付做功能闭环审计：

1. 设计器闭环
   - 组件拖拽
   - 属性配置
   - 保存 / 回显
   - 预览一致性

2. 复杂组件闭环
   - 嵌套组件展示
   - 嵌套组件保存
   - 嵌套组件回显
   - 嵌套组件预览

3. 业务闭环
   - 模板配置
   - 版本发布
   - 基于配置生成业务模板
   - 合同录入 / 回显
   - 数据源查询回填

每项都要明确：入口、保存链路、回显链路、是否有浏览器 E2E 覆盖、是功能缺失还是证据缺失。

### 第 4 章：浏览器 E2E 审计

单独审浏览器级证据，不接受接口或单测替代：

- 页面入口
- 操作步骤
- 期望结果
- 实际结果
- 截图证据
- 是否构成交付阻塞

重点覆盖：

- 拖拽
- 预览
- 属性保存/展示
- 嵌套组件
- 模板到业务模板的完整浏览器链路

### 第 5 章：架构与 DDD 审计

回答：当前代码是否真正达到可迁移的 DDD 结构。

审计维度：

1. 分层是否成立
   - Controller 是否只做 Req/Rsp 与协议适配
   - Application 是否薄层
   - Domain 是否充血
   - Infrastructure 是否只放持久化/外部实现

2. 对象边界是否成立
   - Adapter/Controller：`XxxReq` / `XxxRsp`
   - Application：DTO
   - Domain：领域对象、聚合根、值对象
   - Infrastructure：数据实体

3. DDD 核心语义是否成立
   - 聚合根是否明确
   - 聚合边界是否清晰
   - 值对象是否正确建模
   - 仓储接口是否位于领域层
   - 界限上下文是否可说明
   - 领域对象流转是否可追踪

4. 与外部权威定义的差距
   - 哪些只是命名像 DDD
   - 哪些满足真实 DDD 约束
   - 哪些只是过渡性写法但不能算合格

### 第 6 章：持久化与 MyBatis XML 审计

重点审：

- 是否仍依赖 MyBatis-Plus
- 是否缺少明确 XML
- XML 是否统一为 `xxx.opengauss.xml`
- XML 是否错误携带 `Entity` 命名
- Repository 接口 / 实现边界是否清楚
- 领域对象与数据实体是否混用
- XML 是否足以表达查询语义与迁移要求

并输出：

- 哪些查询/保存已绑死 Plus 风格
- 哪些地方缺 XML
- 哪些 XML 不够表达业务语义
- 哪些 XML 命名不符合 `xxx.opengauss.xml` 约束
- 迁移到公司内的实际改造成本

### 第 7 章：JSONB 与性能审计

重点回答：

1. JSONB 是否被正确利用
2. MVP 几千量级是否存在明显性能风险

审计点：

- JSONB 是否只是存 JSON 字符串
- 查询是否真走 JSONB 路径
- 是否存在索引设计
- 哪些场景需要 EXPLAIN 级证据
- 几千量级下：模板配置读取、查询回填、合同回显、嵌套结构解析是否存在明显瓶颈

### 第 8 章：目标蓝图与迁移路线

这一章定义未来目标而不是当前现状：

1. 目标架构蓝图
   - DDD 分层目标图
   - 包结构目标图
   - 对象流转图
   - 持久化映射关系图

2. 迁移落点
   - 哪些类应挪到 Domain
   - 哪些 DTO / Req / Rsp 应拆分
   - 哪些 Repository 应改为接口 + XML 实现
   - 哪些领域对象应补值对象 / 聚合根语义

3. 整改节奏
   - 理想一次性达标方案
   - 现实分阶段方案
   - 迁移前必须完成项
   - 可延后优化项

### 第 9 章：验收矩阵

输出 4 张矩阵：

1. 功能验收矩阵
2. 架构验收矩阵
3. 性能与 JSONB 验收矩阵
4. 浏览器 E2E 验收矩阵

每一项给出：`通过 / 不通过 / 部分通过 / 无证据`。

### 第 10 章：证据包结构说明

定义证据包的目录、内容和引用方式，保证主报告里的每个结论都能定位到证据。

### 第 11 章：迁移检查表

迁移检查表至少覆盖：

1. 技术栈检查
   - MyBatis-Plus 是否彻底移除
   - 是否全部改成原生 MyBatis + XML
   - XML 是否统一为 `xxx.opengauss.xml`

2. 对象与命名检查
   - 数据实体是否保留 `Entity` 后缀
   - 领域对象是否不带 `Entity`
   - XML 是否不带 `Entity`
   - Req/Rsp / DTO / Domain / Infra 是否越层混用

3. DDD 检查
   - 聚合根是否明确
   - 值对象是否明确
   - 仓储接口是否在领域层
   - 垂直调用链是否成立

4. 交付检查
   - 浏览器 E2E 是否齐全
   - JSONB / 性能证据是否齐全
   - 主报告和证据包是否可直接交付

---

## 5. 冲突处理规则

当不同来源出现冲突时，按如下规则收敛：

1. **业务范围 / 功能边界**：以 `req/req.md` 与 `req/supplement.md` 为准
2. **架构 / E2E / 交付标准**：以用户口述严格要求为准
3. **外部基准**：作为判断“是否符合行业定义与迁移合理性”的补强基准

---

## 6. 输出语言与使用方式

建议整份交付采用中文撰写，便于：

- 用户本人直接阅读和判断
- 研发团队对照落地
- 对上汇报与内部验收复用

同时在涉及技术规范和命名规则的地方，保留英文类名 / 文件名 / XML 命名，以便直接对应代码。

---

## 7. 设计结论

推荐采用**双轨合并交付**：

- 一边做全量审计
- 一边同步产出目标蓝图、验收矩阵与证据包结构
- 最终输出：一份主报告 + 一套证据包 + 一份迁移检查表

这样可以同时回答：

1. 现在是否可交付
2. 为什么不合格 / 哪里不合格
3. 迁移到公司内还差哪些硬约束
4. 应该如何分阶段整改
