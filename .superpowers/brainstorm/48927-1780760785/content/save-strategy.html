配置保存策略

业务人员配置界面如何与后端API交互？

关键问题：何时保存配置？

业务人员配置过程：

添加卡片1
基本信息
添加字段1
合同名称
添加字段2
合同金额
添加按钮
保存合同

问题： 每个操作都调用API保存？还是在内存中构建配置树，最后一次性保存？

方案对比：保存策略

方案1：实时保存（推荐）

流程：每次操作立即调用API

用户操作
① 添加卡片"基本信息"
② 添加字段"合同名称"
③ 添加字段"合同金额"
④ 添加按钮"保存"
API调用（立即）
POST /api/layout-nodes
POST /api/field-defs + field-components
POST /api/field-defs + field-components
POST /api/action-configs
数据库状态
✅ 卡片已保存（ID=1）
✅ 字段已保存（ID=2）
✅ 字段已保存（ID=3）
✅ 按钮已保存（ID=4）
技术实现：
自动保存机制：500ms延迟，避免频繁请求
乐观更新：先更新前端UI，API失败后再回滚
实时预览：每次保存成功后，刷新右侧预览

优点

  • 配置不丢失（随时保存）
  • 实时验证API正确性
  • 支持撤销/重做（后续）
  • 多设备协同（后续）

缺点

  • API调用频繁（500ms延迟可缓解）
  • 网络不稳定时可能失败
方案2：批量保存

流程：内存中构建配置树，最后一次性保存

用户操作
① 添加卡片"基本信息"
② 添加字段"合同名称"
③ 添加字段"合同金额"
④ 点击"保存配置"按钮
内存配置树
{ "layoutNodes": [...], "fieldDefs": [...], "fieldComponents": [...] }
⚠️ 配置只在内存中，未入库
API调用（一次性）
POST /api/templates/save-config
（批量保存所有配置）
技术实现：
前端状态管理：内存中构建完整配置树
批量API：一次性提交所有配置数据
实时预览：基于内存配置树渲染，不依赖API

优点

  • API调用少（一次性）
  • 网络请求集中
  • 预览不依赖API响应

缺点

  • 配置可能丢失（刷新页面丢失）
  • 无法验证单组件API正确性
  • 批量保存失败时全部丢失
  • 不支持多设备协同

实时预览策略对比

方案1：基于已保存数据预览

流程：
① 添加组件 → API保存成功 → GET /api/templates/{id}/schema → 渲染预览
✅ 预览数据与数据库一致，验证真实效果
❌ 依赖API响应速度，预览可能有延迟

方案2：基于内存数据预览

流程：
① 添加组件 → 更新内存配置树 → 直接渲染预览（不调用API）
✅ 预览无延迟，用户体验流畅
❌ 预览数据可能与数据库不一致（保存失败时）

我的推荐：方案1（实时保存）+ 方案2预览优化

✅ 推荐方案：实时保存 + 内存预览优化

保存策略：每次操作立即调用API保存（500ms延迟）

预览策略：同时更新内存配置树 + 调用API验证

优势：配置不丢失 + 预览无延迟 + API实时验证
